Критичные проблемы
1. WebSocket heartbeat memory leak

Файл:

websocket/index.js

Проблема:

const connectedSockets = new Map();

Map очищается только:

по timeout
через disconnect handler

Но если disconnect handler не вызовется корректно при некоторых сетевых сбоях — записи могут копиться.

Также heartbeat cleanup идёт каждые 30 секунд глобальным проходом:

for (const [socketId, info] of connectedSockets)

При большом онлайне это станет bottleneck.

Что улучшить

Использовать:

socket.conn.on('close', ...)

и хранить timestamps компактнее.

Также желательно:

использовать WeakMap где возможно
ограничивать размер connectedSockets
2. Потенциальная race condition в gameLogic

Файл:

services/gameLogic.js

Проблема:

if (room.openedCards.length === 2)

Socket.IO события могут приходить почти одновременно.

Игрок может очень быстро отправить несколько cardClick.

Даже с throttle возможны edge cases.

Возможные баги
двойное начисление очков
рассинхрон openedCards
duplicate match
soft-lock комнаты
Как исправить

Добавить lock per room:

if (room.processing) return;
room.processing = true;

и finally:

room.processing = false;

Лучше сделать полноценный state machine.

3. Нет валидации cardIndex

Файл:

services/gameLogic.js

Сейчас:

room.deck[cardIndex]

Но cardIndex никак не проверяется.

Игрок может отправить:

-1
999999
NaN
string
Это может вызвать
undefined access
corruption состояния
exploit логики
Исправление
if (!Number.isInteger(cardIndex)) return;
if (cardIndex < 0 || cardIndex >= room.deck.length) return;
4. Session store — memory leak в production

Файл:

app.js

Сейчас используется default MemoryStore:

session({ ... })

MemoryStore нельзя использовать в production.

Он:

течёт памятью
не масштабируется
ломается при restart
Нужно

Redis store:

connect-redis
ioredis

или хотя бы SQLite-backed session store.

Это самая важная архитектурная проблема.

5. Возможен XSS через innerHTML

Файлы:

public/admin.js
public/game.js
public/lobby.js
public/i18n.js

Найдены использования:

innerHTML

Если хоть где-то пользовательский username вставляется без escape — будет XSS.

Нужно

Либо:

textContent

Либо sanitize.

Особенно опасны:

usernames
room names
category names
Проблемы безопасности
6. reset password link зависит от headers.host

Файл:

routes/auth.js

Сейчас:

const resetLink = `${protocol}://${req.headers.host}/?reset=${token}`;

Host header может быть подменён.

Атака

Attacker:

Host: evil.com

Письмо уйдёт с evil.com ссылкой.

Исправление

Использовать:

conf.baseUrl
7. Нет password policy

Сейчас:

if (!password)

Минимальная длина отсутствует.

Нужно

Минимум:

password.length >= 8

Лучше:

upper/lower
digits
special chars
8. Username regex разрешает пробелы
/^[a-zA-Zа-яА-Я0-9 _-]{3,32}$/

Проблема:

usernames типа
визуальные impersonation атаки
Лучше
/^(?=.*[a-zA-Zа-яА-Я0-9])[a-zA-Zа-яА-Я0-9_-]{3,32}$/
9. Нет CSRF защиты

API использует cookie-based session.

Но нет:

csrf token
origin validation
Риск

POST requests можно подделать.

Нужно
csurf
либо SameSite=Lax + Origin check
Производительность
10. require внутри socket events

Файл:

websocket/index.js

Сейчас:

require('./gameHandlers')

внутри connection handler.

Node кеширует require, но это всё равно лишняя операция на каждый connect.

Лучше

Вынести наверх файла.

11. leaderboard invalidation неэффективен

Файл:

services/gameLogic.js
setTimeout(() => invalidateLeaderboard(io), 100);

При массовых играх будет spam invalidation.

Лучше

Debounce:

lodash.debounce

или batching.

12. Cleanup intervals не очищаются

Файл:

websocket/index.js
setInterval(...)

Intervals нигде не сохраняются.

При hot reload / тестах это может течь.

Нужно
const cleanupInterval = setInterval(...)

и clearInterval при shutdown.

13. SQLite ALTER TABLE на каждый запуск

Файл:

db.js

Сейчас:

alters.forEach(q => db.run(q, () => {}));

На каждом старте.

Это:

шумит ошибками
тормозит старт
плохая migration strategy
Нужно

Нормальная migration system:

knex
drizzle
sequelize migrations
simple custom migrations
14. Нет prepared abstraction для MySQL/SQLite differences

Есть ручная эмуляция API.

Но SQLite:

this.changes

и MySQL:

affectedRows

ведут себя по-разному.

Это уже потенциальный источник багов.

Лучше сделать единый DAL слой.
